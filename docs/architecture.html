Edge COP Architecture

Every arrow is a topic. Sources publish on the protocol they already speak; everything downstream is a subscription on one hierarchy, cop/{domain}/{event}/v1/{aor}/{iff|source}/{entity}/{status}. Fusion is one subscriber that joins the live streams against reference tables it learned from the same mesh and publishes the enriched record back, once, for everyone.

1End to end

Left to right: what publishes, the two brokers joined by DMR, the subscribers that publish back (alerting, fusion, the agent mesh, and the simulator closing the loop), and the consumers. Nothing polls and nothing talks through an API server; the only thing a viewer may publish is an operator action, which comes back around as an event.

2Where the fusion happens

The fusion service is a single subscriber with five in-memory tables. The tables fill from guaranteed intel topics through q.cop.fusion, which the broker replays from its replay log at startup so a restart loses nothing. The live streams arrive direct. Each join publishes a record that carries the raw entity id in fused_of plus only the fields that were added, so a consumer overlays it on the track it already has.

3The decision record

An operator action is a small message: who, what, on which id. Fusion turns it into one self-describing event by joining it with the target's full record at that moment, every enrichment it holds on that target, the alerts that led to the decision, the elapsed times, and the agent recommendation if there was one. Downstream consumers read that one event; nobody re-joins.

4Agentic flows

The agents are event-driven subscribers on the same broker under their own ACL. Alerts wake them through the Event Mesh Gateway; the time-critical workflows are also run by a standing watch inside the agent host the instant the alert lands, with no model in the path, so an engagement never waits on a 3B model making a tool call. The broker, not the prompt, keeps an agent from firing: acl-agent-mesh may publish cop/agent/>, cop/notify/> and solace-agent-mesh/>, never cop/c2/action/>.

6What the broker enforces

  • Delivery by event type. Tracks are direct with eliding (the next value supersedes the last, no disk). Reports, intel, alerts, actions, agent traffic and decision records are guaranteed and attracted into queues by topic-to-queue mappings, so the spool never fills with track updates.
  • Queues by consumer. q.cop.actions exclusive and ordered; q.cop.alerting, q.cop.cyber, q.cop.decisions non-exclusive so N instances share the load; q.cop.fusion exclusive because it is replayed; q.cop.audit every guaranteed stream once; q.cop.soar bound to a REST Delivery Point, consumed by the broker itself.
  • ACLs on the hierarchy. Source systems publish cop/> and subscribe only to actions and the coalition naval feed; the viewer publishes only cop/c2/action/v1/>; alerting only cop/alert/>; fusion only cop/fused/> and cop/decision/>; the agent mesh never cop/c2/action/>; the CENTCOM cell is confined to cop/*/*/v1/centcom/> in both directions.
  • Two sites, one mesh. The forward broker keeps its sensors and operators talking when the backhaul drops; DMR forwards only what CONUS subscribers asked for when the link is up.
  • Replay. Fusion rebuilds its reference tables from the replay log at startup; the exercise injects, the 1MC actions and the agents' outputs are all on the audit queue like every other event.
